# Devungeon — Product Requirements Document

> **版本**：PRD v1.3（项目自适应世界 + 中英文切换 + 首个像素地牢实现）  
> **日期**：2026-11-13  
> **状态**：完整愿景规范；首轮功能实现见开放 PR #6–#9，跨模块集成与多世界支持仍待实际验收  
> **项目性质**：独立开源、非商业优先、面向 Creative Coding / AI Agent / 游戏爱好者  
> **工作名称**：Devungeon = Development + Dungeon，可在首次正式发布前更名。

## 0. 执行摘要

**Devungeon 是一个根据真实软件项目的结构、产品定位与设计语言，生成独特、可探索、可游玩、可工作的游戏世界的开源平台。** 像素地牢是首个可玩的参考世界包，不是所有项目的必选形式。

- **看世界**：AI 理解任意规模项目的功能结构与依赖，通过 AI 建议、用户选择与已实现的世界包生成适配的场景；真实开发与验收事件驱动世界演化。
- **在世界里工作**：在 3D 世界中找到主管 Agent 与执行 Agent，对话、查看工作、分派任务、核对证据、处理授权。
- **在世界里玩**：玩家在可进入区域自由探索、战斗、刷副本、收集游戏物品；Agent 的真实工作不会因玩家游戏而中断。
- **与世界共同成长**：每次真实交付使房间、通道和世界发生持久变化；未实现区域可以从安全视角预览，但不可作为已通关区域进入。

核心标语（候选）：**Your agents are working. You're playing. Your world is growing.**

**主要目标不是赚钱。** 首要目标是好玩、令人惊艳、可拍成视频、容易分享与复现、适合开源协作和创意技术比赛。真正有用的工作台是它的第二条价值线；不能为了管理功能牺牲游戏乐趣，也不能为了游戏效果篡改真实项目状态。

### 关于“第一版完整构想”

本文 **v1.0 是当前已讨论内容的完整产品蓝图**，不是只记录一个缩水 MVP。实施可分可测里程碑，但当前确认的核心方向都必须被纳入设计、协议和验收计划。后续新增灵感通过 PRD 变更记录扩展，不必现在过早封死玩法。

## 1. 用户、场景与成功标准

### 用户

1. **产品创作者 / 非技术使用者**：不愿逐行读代码，却要知道 AI 究竟做成了什么、哪些能力能用、卡在何处。
2. **AI Native 开发者与 Agent 团队**：同时使用 Claude Code、Codex、其他 Agent，想要可观赏也可操作的统一空间。
3. **游戏爱好者、开源贡献者、观众**：即使对项目管理没有需求，也愿意进入世界玩、围观 Agent、制作主题、分享片段。

### 必须成立的体验

- `第一次进入`：几秒内理解“这是我的项目世界”，无需学习传统看板用法。
- `工作进行中`：看见 Agent 在场景中具象地行动，点开能找到可追溯的真实事件，而非凭空播放的特效。
- `项目有变化`：新模块出现新房间；修复或验收只改变对应区域；原有布局不被整图随机洗牌。
- `用户无聊时`：不关闭项目也能进入游戏战斗，工作的 Agent 同时运行。
- `需要干预时`：走到 / 选择主管或执行 Agent，发自然语言指令或检查进度，敏感操作需要明确授权。
- `陌生项目`：一个简单 Landing Page 和一个多模块 Agent 系统能生成不同规模、不同结构的世界，而不是固定房间模板。

### 成功定义（非收入指标）

- 玩家能完整游玩，而不只是浏览静态 3D 展示。
- 真实进度改变地图，展示的信息有可信来源与验收证据。
- 至少一种真实的 Agent 系统形成指令→执行→事件→画面→结果核验闭环。
- 两个结构显著不同的项目能够正确生成、持续更新世界。
- 可独立启动、无付费账号强依赖、有许可证清晰的美术与代码、能录制诚实的 30–60 秒演示。

## 2. 产品原则与非目标

1. **Fun first**：角色、移动、战斗和音画反馈必须足够好玩；不是把 Jira 伪装成地牢。
2. **Project truth**：真实项目进度可核对、可追溯、可反驳；游戏状态不能回写为代码质量或交付状态。
3. **One world, two systems**：工作系统和游戏系统共享环境、角色与叙事，不共享“成功判定”。
4. **Agent-designed, engine-executed**：AI 产出语义世界蓝图，程序化引擎负责可玩几何、碰撞、导航、可达性；不要让 LLM 每次手工生成不受约束的 3D 代码。
5. **Stable but alive**：稳定 ID、确定性布局、增量扩建，可回放世界历史。
6. **Open by default, private by design**：本地优先、显式连接、最小权限；公开访客只能看到用户选择公开的内容。
7. **Composable**：项目适配器、Agent 适配器、世界生成器、主题、游戏玩法互相解耦。

**非目标**：v1 不追求取代 IDE、完整代码审查工具、云端自主编程平台或专业游戏引擎；也不追求用金币/怪物血条推测任务实际完成百分比。

## 3. 通用项目事实与首个地牢世界包的语义映射

| 产品真实概念 | 世界概念 | 规则 |
|---|---|---|
| 整个仓库或产品 | World / 游戏世界 | 一个项目持有稳定的产品世界身份，可选择不同体验世界包 |
| 领域、子系统 | Zone / 区域或楼层 | 由项目能力划分，不必与目录结构一一对应 |
| 可独立体验或验收的功能 | Room / 房间 | 主要交互节点、稳定身份 |
| 功能/任务依赖 | 门、桥、机关、传送门 | 前置依赖决定通路是否开放；显示真实原因 |
| Issue / Task / Bug / 风险 | 敌人、怪群、事件、陷阱 | 动画是任务活动隐喻；详情展示真实任务 |
| 里程碑、复杂阻塞 | Boss / 特殊副本 | 关键任务集合的视觉形态；只有验收才算交付通关 |
| Agent（主管/执行/审查） | NPC / 战斗伙伴 / 角色 | 角色关联稳定 agent_id 与能力 / 实时状态 |
| 实际交付成果 | 宝箱、建筑、区域成长 | 可点击回到 PR、提交、测试、部署等证据 |
| 未规划清楚的想法 | 远方迷雾 / 尚未勘探区域 | 明确标示“未知”，不伪造具体关卡 |

下面的 Zone / Room / Door / Boss 仅是**首个地牢世界包**的空间表达；城市包可映射为街区、建筑和道路，空间站包可映射为舱室、连接器与维修活动。这些都不能改变项目真实实体与状态。游戏表现不是唯一映射：项目主题、Agent 世界设计师与用户可决定“数据库是否是图书馆、凭据系统是否是金库”。**真实实体、依赖、状态和证据不可任意杜撰。**

### 房间的真实状态机（独立于游戏）

`planned` 未开始 → `ready` 可开始 → `active` 工作中 → `review` 待验收 → `accepted` 已验收。

允许 `blocked`（阻塞）、`failed`（失败）、`regressed`（验收后回退）和 `archived`（退出当前范围）；其中 `review` 不等于 `accepted`，关闭 Issue 或合并 PR 也不必然等于功能已可用。

- **planned / 未解锁**：可远观、旋转和放大镜头查看设计与预期，但玩家无法进入房间或越过门；未定义区域保持迷雾。
- **active**：Agent 角色进入，基于真实事件播放工作/战斗动画；不可通过血条自行宣布完成。
- **blocked / failed**：警报或精英怪形态，点击可见阻塞源、负责人、下一动作。
- **review**：敌人暂歇、宝箱封印，展示验收证据与待确认事项。
- **accepted**：房间可进入，建筑亮起、宝箱可开、下一区域按依赖解锁。
- **regressed**：仍保留历史探索记录，但清楚显示当前能力失效、限制再次通过；不抹去事件历史。

## 4. 首个世界包：可玩的原创 2.5D 像素地牢

### 4.1 相机、探索与世界

- **首个 pixel-dungeon 世界包采用《元气骑士》类型的俯视角像素地牢氛围，原创 2.5D 美术**：真实 3D 房间、碰撞与摄像机，配合像素精灵、16×16 基础纹理网格、最近邻采样与利落战斗反馈。参考的是玩法节奏与视觉语言，**不复制《元气骑士》的角色、精灵、UI、关卡、美术资源或音乐**。自由旋转先验证 90° 分段方向；非整数角度需验证像素/遮挡一致性。
- WASD / 摇杆移动；鼠标或触控旋转、平移、缩放；可锁定角色、自由镜头、切回全览。
- 已通过的房间可进可互动；锁定房间只能通过观察视角提前看，设置碰撞、门和导航双重阻止越界。
- 区域可携带独特视觉主题（魔法、机械、赛博、森林、遗迹），允许 UI 调整画风；工程语义与美术主题分离。
- 自动生成必须验证房间可达性、边界、碰撞、相机遮挡、生成种子稳定性；地图大小随复杂度缩放，不能让小项目被巨大空地稀释。

### 4.2 工作画面

- 每个 Agent 有角色身份、名字、职业 / 图标、当前状态和所属任务。
- 开发：攻击 / 施法；检索资料：探索 / 侦察；测试：检定 / 魔法阵；代码审查：守门 / 鉴定；阻塞：护盾 / 异常；完成：庆祝 / 奖励。
- 多 Agent 协作可以组队，主管 Agent 在指挥区显示计划、派遣和汇总；实况事件要有 `observed_at` 与源证据。
- 事件延迟、断线、权限不足时可显示“连接断开”“事件已过期”“仅为演示”，不可伪装成实时。

### 4.3 玩家娱乐游戏循环

- 玩家角色可以移动、闪避、攻击、使用技能、挑战独立怪物与副本、拾取道具、解锁**游戏内**成长奖励。
- 游戏循环和 Agent 工作彼此独立；用户正在刷怪时，后台真实 Agent 可以继续工作并弹出非阻断通知。
- 玩家的伤害 / 资源 / 难度与 GitHub、CI、真实任务验收**没有逻辑耦合**；打赢娱乐 Boss 不等于合并 PR，输掉游戏也不会回滚代码。
- 世界共享视觉和背景故事：完成工作可能解锁新的游戏区或纯外观奖章，但绝不反向赋予真实系统授权或伪造验收。
- 支持安全暂停本地游戏、恢复游戏和保持工作事件展示的分离控制。

### 4.4 观战、回放和分享

- 观战 / 游览模式：无需操作游戏战斗即可自由查看区域和 Agent 事件。
- 时间轴回放真实开发历史：选择某段时间，重播当时的已记录事件与地图变动；区分回放和当前实时状态。
- 便于录制 30–60 秒视频：电影镜头、可隐藏 HUD、明确显示真实接入源与演示源。
- 可导出**经过用户显式审核的**世界截图、视频脚本与脱敏项目快照；公开分享前防止私有仓库名、消息、代码片段、凭据泄露。

## 5. AI 世界设计师：如何适配不同项目

### 初次导入

1. 用户选择项目源：本地目录、手动 JSON、GitHub，或 Agent/平台适配器。
2. 读取可获取的结构化证据：README、目标、功能文档、目录、Issue、PR、测试、部署状态；缺失的部分标记 unknown。
3. 提炼 `ProjectGraph`（产品能力、模块、功能、任务、依赖、证据），不直接以“代码文件=房间”。
4. 由 AI 世界设计师为每个功能和区域提出叙事、主题与布局偏好，并保存设计理由 / 来源；用户可以编辑蓝图。
5. 确定性布局器根据蓝图、固定 seed、可用预制件生成可玩的世界，先做碰撞与可达性检查，再呈现动画。
6. 保存 world_id、entity_id、布局与版本快照。

### 持续演化

- 新功能：向相应 Zone 增加房间或支线，不整图重排。
- 新依赖：更新门和导航，提供变更原因；已有探索记录不能无故丢失。
- 重命名 / 拆分：使用稳定 ID 和迁移关系维护历史；重大结构变更由用户预览并确认。
- 删除 / 停用：保留可追溯历史，世界中的遗迹可作为视觉表达，不再宣称当前可用。
- AI 不能凭猜测把任务置为 `accepted`；不可信模型输出必须经 schema 校验与来源比对。

**为什么不是统一模板**：共享的是可信项目语义、Agent 事件和可验证状态；用户选择的世界包决定空间隐喻、外观和玩法。同一项目可以选择像素地牢、城市、空间站、展馆等（只有已实际实现并通过验证的世界才可以标记为可玩）。项目规模与依赖约束地图，AI 不应替用户固定一种风格。见 ADR-0002-PROJECT-ADAPTIVE-WORLDS.md。

## 6. Agent 工作台（Workspace in World）

### 6.1 角色类型

- **Supervisor Agent**：站在指挥大厅，展示目标、计划、任务分配、审批请求、队员工作情况；可由适配器连接真实主管。
- **Worker Agent**：在目标房间执行工作；展示当前任务、最近事件、输出 / PR / 测试状态。
- **Reviewer / Tester Agent**：负责审查与核验；不能仅通过对话宣称通过就自动改变业务验收状态。
- **Player / Owner**：可游玩、观察、对话、下发工作请求和审批，但须遵守底层系统实际权限。

### 6.2 交互

- 点击或靠近角色打开轻量 Agent 卡片；查看状态、任务、最近活动、链接到原始证据。
- 对主管/执行 Agent 自然语言对话；可以创建目标、咨询进度、请求调度、请求复审、停止或重新分派（**以适配器实际支持的能力为准**）。
- 主管可展示分派方案和 Agent 任务路径，在世界中以出发、组队、传送、战斗演出。
- Agent 发送更新，世界中即时出现提示；UI 支持失败重试、空结果、超时、断线、回放状态提示。
- 如果尚未连接真实 Agent，明确标记 `DEMO / SIMULATED`，且禁用或模拟执行动作，不冒充真实对话或控制。

### 6.3 权限与审计

- 读取仓库/状态默认最小权限；发送指令与执行外部动作采用明确的 capability 声明。
- 删除资源、对外发布、真实购买、持久登录凭据操作、生产变更等高风险动作要求真实授权界面；游戏道具不具备授权效力。
- Agent 连接走受信任的本地桥接 / 服务端，**前端浏览器不接收原始访问令牌或密钥**。
- 每项指令记录 `command_id`、请求者、目标 Agent、权限、结果、真实时间与可审计来源；支持取消、重试与幂等。
- 连接范围按项目隔离；公开观众不得调用私有工作 Agent。

## 7. 通用数据与适配协议

必须分离三类事实：

1. **ProjectSnapshot（可验证的产品事实）**：功能、依赖、验收状态、证据、时间戳、来源、未知项。
2. **WorldBlueprint（生成出来的场景设计）**：Zone、Room、门、摆设、出生点、碰撞和布局 seed；同一产品可用不同主题渲染。
3. **LiveEvents（真实运行中的事件流）**：Agent 开始/暂停/完成动作、PR、CI、Issue、指令、验收、失败与断线。

另外维护 **GameState（纯游戏）**：玩家位置、生命、技能、敌人、掉落与本地成就；不得写回 ProjectSnapshot 的验收结果。

最低约定字段：`schema_version`、`project_id`、`entity_id`、`status`、`source`、`source_url_or_ref`、`observed_at`、`verified_at`、`confidence/unknown`、`revision`；关键事件包含 `event_id` 用于去重与回放。

**官方适配器范围**：手工 JSON（立即可用以验证协议）、本地项目 / GitHub（真实事实）、Claude Code 与 Codex 的事件映射、可插拔的 Crew Agent 桥接。不是所有工具都保证暴露完整生命周期事件；适配器必须明确声明哪些是观测、哪些是推断、哪些是未知。其他适配器由社区扩展。

## 8. 界面和交互规格

### 主要界面

- **World Entry**：选择 / 导入项目、生成世界、选择角色与主题、查看同步状态。
- **World Scene**：优先显示 3D 世界，HUD 尽量克制；镜头可切换全览、跟随、自由、观战。
- **Agent Panel**：角色信息、自然语言聊天、正在执行的任务、事件、许可范围与取消/审批。
- **Room Panel**：用非技术语言解释功能、已做成什么、证据、阻塞、未完成项、验收条件。
- **Quest Log**：模块/里程碑、真实状态、负责人、依赖、证据；保留传统列表入口以便快速操作。
- **Game HUD**：玩家血量、装备、技能、地图与战斗反馈；不污染真实进度展示。
- **Timeline**：历史回放与世界增量变更。

### 操作约束

- 在鼠标/键盘为主的桌面浏览器可完整体验；移动端只承诺适配后的基础游览，完整战斗控制另行验证。
- 包含色盲可辨识的状态标记、字幕 / 静音选项、可关闭屏幕抖动与降低粒子特效选项。
- 为 WebGL 不可用或设备性能不足时提供 2D / 文本项目事实视图，不应隐藏关键工作证据。

## 9. 建议技术方案与边界

**首选技术栈（待垂直切片实测）**：TypeScript + React + Vite；Three.js / React Three Fiber（3D UI 与场景）、Drei（通用辅助）、Rapier（碰撞物理）；状态管理可用 Zustand；Zod/JSON Schema 做数据边界校验；轻量 Node 本地桥接服务读取受授权项目事实，事件持久化先用 SQLite 或本地文件日志；实时更新可选 SSE / WebSocket。优先使用免费、活跃、许可证兼容的美术与声音资源，必要时自主设计。

高层数据流：

`GitHub / local / Agent connectors → validated project graph + live events + approved product design signals → AI experience suggestions + user choice → installed world pack (spatial mapping, renderer, gameplay) → interactive world + shared Agent workbench`。

**控制流必须独立**：`user command → permissions/approval → Agent adapter → external agent → observed result → event log → display`。世界动画不能绕过权限去直接发操作。

**替代方案**：Godot 更偏成熟完整游戏制作工具，但 Web UI、独立 Agent 交互面板和浏览器原生集成成本可能较高；首轮试验优先 Web 原生 Three.js 栈，若战斗与性能上限证明不够再评估 Godot/其他引擎。

### 项目结构建议

```text
apps/web/                 3D 前端、交互面板、游戏 HUD
apps/bridge/              本地可信连接桥；项目/Agent 授权边界
packages/world-schema/    版本化的项目事实与世界协议
packages/project-adapters/本地、GitHub、手动 JSON 适配器
packages/agent-adapters/  Claude Code、Codex、Crew 等接入
packages/world-generator/ AI 语义图 → 布局、增量构建
packages/dungeon-engine/  首个像素地牢世界包：导航、角色、战斗、像素渲染
packages/event-log/       去重、事件溯源、回放、投影
examples/                 脱敏和合成示例
assets/                   具备清晰许可的原创/兼容资源
docs/                     PRD、架构、验收与决策日志
```

上述是推荐目标结构，不要求一次创建无实现的空包；按真实可工作的纵向切片逐渐拆出公共包。

## 10. V1 功能要求与验收依据

> 下面为**首个完整产品版本目标**，非“已经实现”。可按第 11 节拆分内部迭代，但对外宣称 V1 完整需满足这些条件。

| 编号 | 要求 | 可操作的验收 |
|---|---|---|
| FR-01 | 从两种不同真实项目结构生成世界 | 新建两项目，zone/room/依赖数量与拓扑不同，可追溯来源 |
| FR-02 | 稳定的增量世界演化 | 加入新功能只新增或修改相关房间；已验收房间位置不无故变化 |
| FR-03 | 3D 自由探索与镜头 | 角色行走、避障、镜头旋转缩放；看得到但进不去上锁区域 |
| FR-04 | 可玩的战斗循环 | 实际操作攻击、躲避、命中、生命和奖励，能完整打一场独立副本 |
| FR-05 | 真实事件驱动 Agent 行动 | 至少接入一种真实 Agent 的动作事件并与角色演出对应，能点击源证据 |
| FR-06 | 工作/游戏独立 | 游戏击杀不会改变真实任务状态；游戏中收到真实 Agent 更新 |
| FR-07 | 主管/执行 Agent 工作台 | 至少一种真实 Agent 连接可双向对话、提交可支持的指令并查看结果 |
| FR-08 | 真实状态与验收 | planned/active/review/accepted/blocked/regressed 不混淆；验收证据可查看 |
| FR-09 | 自适应项目布局 | 简单 Landing Page 与复杂 Agent 仓库可生成不同规模和形态的可玩地牢 |
| FR-10 | 安全连接、审批与隐私 | 令牌不出现在前端；危险动作审批；只读访客不能指挥私有 Agent |
| FR-11 | 断线、过期和演示标记 | 模拟数据有显著 DEMO 标记，事件过期不会伪装实时 |
| FR-12 | 本地可启动、易分享与开源 | 文档可复现启动；视频演示可用；许可证、贡献指南、测试结果齐备 |
| FR-13 | 世界主题/蓝图可调整 | 用户可编辑语义主题和世界外观，状态事实不受美术设置影响 |
| FR-14 | 历史回放 | 至少可回放任务状态与世界进化，并明确与实况区分 |

### 建议的工程指标（初始目标，非已验证数据）

- 目标桌面设备上含约 20–40 房间、5–10 角色时，普通场景交互目标稳定 ≥30 FPS，尽量达到 60 FPS；以实测调整细节。
- 正常输入与交互无明显卡死；失去实时连接时可离线游览已缓存的地图。
- 同一个固定 seed / project revision 在同一生成器版本下能得到相同拓扑，增量变更可测试。
- 数据协议有 JSON Schema 校验、事件去重、权限拒绝、证据缺失、错误恢复测试。

## 11. 开发顺序：完整愿景下的可测量切片

**S0 — 仓库与协议**：PRD、许可证、架构、事件规范、两个合成项目示例、最小可复现开发命令；没有游戏时不能宣称已完成产品。

**S1 — 可玩地牢**：真实 3D 房间、角色移动、镜头、碰撞、锁定区域远观、独立战斗循环；用合成事实展示，但显著 `DEMO`。

**S2 — 项目世界编译器**：导入两种项目、生成语义图、世界布局、保存和增量更新、状态详情与证据。

**S3 — Agent 实时接入**：至少一个真实 Agent 事件源、角色动作、状态同步、事件日志、错误与时间线回放。

**S4 — 工作台闭环**：主管与执行 Agent 对话、权限、任务发起、回复和执行结果联动；与游戏并发运行。

**S5 — 完整 V1 发布验收**：玩法、视觉、性能、可访问性、脱敏、README、安装、示例、真实端到端录像与开源比赛材料。

这些是**工程实施阶段**，并不删去第 10 节完整 V1 产品范围。每阶段只有真实跑通才标记完成。

## 12. 安全、开放和许可证

- 推荐代码采用 **Apache-2.0**；明确保留第三方依赖许可与声明。若项目最终使用了不同许可证的改造代码，先做兼容性审查。
- 美术音效采用自制、CC0 或经过许可核验的资源；**参考《元气骑士》的游戏体验，不复制其角色、UI、精灵图、音乐、音效或关卡**。
- 仓库默认公开前必须确认不包含 Crew 私有仓库数据、真实对话、访问令牌、未公开商业信息；提供合成示例即可。
- 本地授权应按项目和 Agent 分离；公开可分享的是脱敏快照而非默认公开实时工作区。
- 正式比赛录像说明真实接入部分与预演/示例数据，避免以录屏冒充真实闭环。

## 13. 主要风险与已选策略

| 风险 | 处理原则 |
|---|---|
| 好看但不能玩 | 游戏操作手感、战斗和地图游玩必须有独立验收 |
| 游戏隐喻误导项目状态 | 工作事实与 GameState 分开存储；必须有证据链接 |
| LLM 生成房间太随机或不可达 | AI 输出结构化蓝图；布局器确定性、碰撞和路径自动检查 |
| 每次更新整张地图改变 | 稳定 ID、版本化地图、增量迁移与回放 |
| Agent 接入能力参差不齐 | 显式 capabilities；没有真实连接就标 DEMO；只展示真实可用的控制 |
| 对外发布泄露私有信息 | 连接凭据保留在可信桥接层；显式脱敏审核后再分享 |
| 浏览器 3D 性能波动 | 预制件复用、LOD/实例化、资源预算、降质/2D 事实视图 |
| 美术侵权 | 视觉参考只借鉴玩法原则、所有实际资源独立制作 / 许可核验 |

## 14. 未来灵感扩展区（未纳入 V1 必要验收）

## 15. 待验证的关键技术假设

1. 一种 ProjectGraph 能否把极小项目和复杂 Agent 项目映射为不同但同样可玩的世界？
2. 不同 Agent 产品能暴露多少真实可追溯事件？不能观测时怎样优雅退化？
3. 在 Agent 自主工作与玩家手动游戏并发时，如何使视觉活动热闹却不损害前端性能？
4. 用规则加 AI 世界设计师，能否生成有审美区别且足够稳定的地图？

每项假设用真实小样、对照输入、测试记录验证，失败时优先调整方案而不是无条件增加架构复杂度。

## 17. v1.1 视觉与工具尽调补充（2026-11-13）

**已确认视觉决策：** Devungeon 的标志性内置主题是 **像素风俯视角地牢游戏**，玩法节奏参考《元气骑士》类型作品，而不是默认光滑的 3D 卡通/写实城堡。采用原创 2.5D：真实空间结构、角色碰撞和镜头 + 精灵动画/像素纹理；允许观察未完成房间，但不能进入未验收区域。不能直接引用或重绘复制受保护的游戏资产。见 [完整美术方向](VISUAL_DIRECTION.md)。

**技术路线与成熟方案：** 前端仍优先 Web 原生 Three.js / React Three Fiber / Rapier，像素质感由风格指南、Sprite、像素密度、最近邻贴图和镜头约束实现；rot.js 可实验性用于地牢初始拓扑，但项目依赖及房间稳定性需要专用布局约束；PixiJS / Phaser / Godot 作为记录的替代方案。美术先调查可复用、可公开分发的 Kenney CC0 像素素材和 Pixelorama；实际资源尚未导入。见 [工具与 Skill 尽调](TOOLS_AND_SKILLS.md)、[素材授权登记](ASSET_PROVENANCE.md)。

**Agent 协作：** 仓库新增可版本化、项目专属 Skills，包括像素美术、可玩验证、世界编译器、真实事件、安全工作台与依赖尽调；Claude Code 与 Codex 读取方式见仓库根目录 CLAUDE.md / AGENTS.md。Skills 的存在 **不代表** 第三方工具已经安装，也不代表真实连接已完成。

**新增视觉验收：** 桌面浏览器必须能完成真正像素地牢的移动/攻击/闪避/击中反馈，录像与固定视口截图要验证像素清晰、角色方向一致、镜头旋转后可读性、锁门碰撞、Agent DEMO/实况标识；实际性能需测量。这是既有 V1 完整验收的细化，不是删减功能。


## 18. v1.2 中文优先与中英文切换（2026-11-13）

**正式产品要求：Devungeon 首次启动默认简体中文（zh-CN），支持完整的中文 / English（en-US）实时切换。** 这是面向不熟悉英文的产品创作者的重要可用性能力，必须覆盖游戏与 Agent 工作台，而非只翻译按钮。

- **完整范围：** 进入游戏、操作帮助、HUD、战斗结果、地牢/房间解释、项目进度、Agent 状态、任务对话、审批权限、错误和连接提示、无障碍标签都需要双语。
- **无扰切换：** 用户在任意游戏阶段随时切换语言；不能刷新、重置战斗、破坏任务、改变审批结果或重新生成地图。本机保存选择，首访默认中文。
- **项目事实与翻译严格分离：** 稳定 ID、任务状态、依赖、地图 seed、时间、真实事件与授权内容保持不变；原始 GitHub/Agent 文本可追溯；中文说明不得凭空编造事实。
- **架构责任：** WIZARD 统一 i18n 资源和状态，HERO 接入所有游戏文案，BUILDER 提供语言无关的世界图与可本地化的展示文字，SCOUT 保留原始事实并提供来源。
- **隐私与版权：** 静态界面翻译完全本地运行；第三方在线翻译或处理私有代码/对话须单独获得授权。
- **验收：** 双语言实机浏览器检查、资源 key 完整性、切换时状态不变、中文字体可读性和外部原文保留。见 [中英文产品规范](I18N.md) 与 [Issue #10](https://github.com/orionaster/devungeon/issues/10)。

此补充属于完整 V1 产品范围。旧文档中的“implementation not started”描述仅针对原始设计稿时间点，实际各开发分支进展以 PR 和独立验收为准。


## 19. v1.3 产品方向变更：项目自适应游戏世界（2026-11-13）

**正式决定：** 不是把每个项目套进固定的像素地牢。Devungeon 应当根据项目的产品类型、功能结构、视觉品牌语言、目标用户与创作者偏好，**建议具有不同空间结构、美术与游戏玩法的世界**，并由用户最终选择。这里的“产品语言”是 design language，不是中文/英文或开发语言。中英文 UI 规则继续独立遵守 docs/I18N.md。

例如 AI Agent 产品可以选择像素地牢；业务 SaaS 可以选择城市（建设与街区探索）；航天项目可以选择空间站（模块连接与维修）；设计产品可以选择博物馆（展厅探索与收藏）。这只是可选创意，不构成固定映射；用户也可以把 Agent 产品改成星际战舰。

**架构补充：** 真实 ProjectSnapshot/Agent 事件和验证状态与世界的渲染、玩法完全解耦。AI 世界设计师基于已授权的设计信号提供候选方案与理由，用户预览和选择，然后由已安装、通过验证的世界包负责生成场景与可执行玩法。WorldExperience sidecar 记录候选世界类型、插件、依据、选择、可用性；不能通过切换世界改变任何验收事实、授权、原始证据或真实 Agent 工作。

**渐进实现：** 目前像素地牢 S1、地图生成 S2、数据 S3、工作台 S4 的既有成果继续集成，不推倒重来。新增多世界协议后，需做第二种世界的**实际不同玩法**测试，不能只换皮或者用两份 JSON 假装两款游戏已经可玩。概念中的城市、空间站、美术馆尚未实现。

**正式来源：** [ADR-0002 — Project-adaptive worlds](ADR-0002-PROJECT-ADAPTIVE-WORLDS.md)；[WorldExperience draft schema](../schema/world-experience.schema.json)。

### 新增验收 FR-15
从同一份源项目快照，能够通过用户选择运行至少两种空间/玩法不同且已验证可玩的世界；原始功能 ID、依赖、验收状态、真实 Agent 事件和权限均不发生改变。首次实现可以先交付像素地牢，再在完整 V1 发布验收前完成第二种世界的真实运行验证。
